Every <GlossaryTerm term="Lineth" /> node runs a consensus client,
[Maru](../../reference/repos.mdx#maru), which orders blocks and propagates them to peers, and one or
more execution clients, which execute transactions and maintain EVM state.
Maru communicates with its execution clients over the standard Ethereum
[Engine API](https://github.com/ethereum/execution-apis/blob/main/src/engine/common.md).

Any node can also expose [JSON-RPC](../rpc-services.mdx) to serve applications, users, or internal
services, either publicly or only within the operator's network.

## Consensus client: Maru

[Maru](../../reference/repos.mdx#maru) implements
<GlossaryTerm term="Quorum Byzantine Fault Tolerance (QBFT)">QBFT</GlossaryTerm> consensus and runs
on every node, in one of two roles:

- **Maru validator:** Proposes and votes on blocks as part of the QBFT validator set.
  Maru requests a payload from its dedicated Linea Besu execution client, then signs and broadcasts
  the resulting block.
- **Maru non-validator:** Receives blocks from peers and imports them into its execution clients,
  without proposing or voting.

In both roles, Maru manages validator sets, provides P2P block propagation, and exposes API
endpoints for monitoring and control.

A single Maru consensus client can drive more than one execution client.
Alongside the execution client it uses for block building or import, either Maru role can drive
additional <GlossaryTerm term="Follower execution client">follower execution clients</GlossaryTerm>,
configured under [`follower-engine-apis`](../../../stack/reference/linea-maru-options.mdx#maru).
A follower execution client doesn't run its own Maru instance.

For Maru TOML configuration keys, see the
[Maru options](../../../stack/reference/linea-maru-options.mdx).

## Execution client: Linea Besu

Any Ethereum execution client that implements the Engine API can serve as a Lineth execution client
and integrate with Maru, including Linea Besu, Besu, Geth, Erigon, and Nethermind.
This promotes client diversity and compatibility with existing Ethereum node tooling and
infrastructure.

[Linea Besu](../../reference/repos.mdx#linea-besu-upstream) is a distribution of
[Besu](https://docs.besu-eth.org/) that bundles several Lineth-specific plugins with preset startup
profiles.
These plugins implement the protocol functions that a standard Ethereum client doesn't provide:
trace generation for the <GlossaryTerm term="Prover">prover</GlossaryTerm>, Lineth block-building
rules, <GlossaryTerm term="State manager">state manager</GlossaryTerm> integration, and the `linea_`
RPC namespace.

Each Maru validator requires a dedicated Linea Besu execution client with
<GlossaryTerm term="Sequencer">sequencer</GlossaryTerm> plugins.
A Maru validator paired with such a client is a
<GlossaryTerm term="Sequencer node">sequencer node</GlossaryTerm>, and that pairing is what produces
canonical blocks.
During block building, the sequencer generates <GlossaryTerm term="Tracer">traces</GlossaryTerm> to
ensure blocks remain within prover limits.
Execution clients that generate prover input traces must also use Linea Besu.

Nodes that only import blocks or serve standard Ethereum JSON-RPC can run any Ethereum execution
client.

This makes the two layers separately configurable, but not symmetrically scalable.
Because every validator needs its own Linea Besu, adding validators also means adding execution
clients.
Follower execution clients can be added independently, without adding more Maru nodes.

For the full plugin set and its configuration, see the
[Linea Besu plugin reference](../../../stack/reference/linea-besu-plugin-options.mdx).
