The prover is a <GlossaryTerm term="Lineth"/> module that turns execution traces into
<GlossaryTerm term="zk-SNARK">zk-SNARKs</GlossaryTerm>.
These zk-SNARKs enable the <GlossaryTerm term="Finalization layer">finalization layer</GlossaryTerm> to
accept a Lineth state transition without re-executing any transactions.

Proof generation is computationally intensive, so deployments run the prover as one or more dedicated
instances rather than inside the execution client.

:::tip Evolving toward RISC-V

Lineth is evolving toward a [RISC-V proving architecture](./risc-v-overview.mdx), in which guest
programs define the computation to prove.
It is in development and is not yet part of any Lineth deployment.

:::

## How it works

The <GlossaryTerm term="Coordinator">coordinator</GlossaryTerm> drives the prover.
It writes each proof request, along with the <GlossaryTerm term="Conflation">conflated</GlossaryTerm> traces produced by the
<GlossaryTerm term="Tracer">tracer</GlossaryTerm>, to the directories the prover watches, and collects the
finished proof from the same place.
Those traces stay within the [module limits](./module-limits.mdx) that keep a batch provable.

The prover produces three kinds of proofs:

- **Execution proofs** show that the transactions in a batch executed correctly.
- **Compression proofs** show that a blob's compressed data expands to the batches it stands for.
- **Aggregation proofs** combine the proofs for several blobs into the single proof submitted at finalization.

Each proof is built in two stages:

1. [Corset](./corset.mdx) expands the trace data into the full constraint system, the
    arithmetization the prover proves against.
2. The proving system reduces that expanded data to an inner proof, then wraps it with the
    [gnark](./gnark.mdx) library into an outer proof: the zk-SNARK that a verifier contract on the
    finalization layer can check cheaply.

Because the proof accompanies the data it proves, anyone can confirm that a state transition is correct
by checking the proof onchain, instead of trusting the operator or re-executing the transactions themselves.

:::info
The proving system uses reference strings from the [trusted setup](./trusted-setup.mdx).
:::
